Handling Multiple Clients

In order for a DNS server to handle multiple clients each second,
it never stores client state (like IP/port) for longer than a few
milliseconds. Instead, it relies on stateless multiplexing.

Usually it involves using an event loop:

    - The server has a single socket (or a small pool of sockets)
    - It issues a non-blocking recvfrom() in a tight loop
    - When a packet arrives, the server processes it synchronously
      in the event loop. Because a DNS lookup over UDP takes 
      microseconds (if cached), the server can process 10,000 
      packets sequentally on a single CPU core before the first
      client even times out.

The biggest challenge is when the server doesn't know the answer
and must ask another upstream server (e.g., 8.8.8.8). This takes
100-200 milliseconds, which is an eternity in CPU time.

To fix this, the server should use internal pipelining:

    - When the server forwards a query upstream, it generates
      a unique internal token
    - It stores the original clients IP/Port in a tiny in-memory
      hash table, keybed by that token
    - It then movs to the next client in the event loop
    - When the upstream server finally replies, the packet arrives
      back at the DNS server. The server looks at the incoming TXID,
      finds the token, looks up the hash table, retrieves the original
      client IP/Port, rewrites the packet, and fires it off to the
      original client.
